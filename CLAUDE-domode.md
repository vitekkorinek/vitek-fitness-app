### View-only Do Mode — CLIENT (read-only, July 2026)
Opening client Do Mode with `?viewOnly=1` is a **read-only browse view** — nothing editable. Vitek's rule: **View = look at video/notes/weights.** The one start affordance is the header **START pill for a PAST-day completed session** (`canRepeatViewed` — repeat it today), which runs a confirm before `guardStart(beginSession)`; a session completed TODAY shows the FINISHED pill and nothing startable. - Params: `viewOnly=1` + `viewMode` (`finished` | `start` | `none`). `isViewOnly = viewOnly === '1'`; `showFinishedPill = isViewOnly && viewMode === 'finished'`.
- **Header pill:** a running session always wins (timer + FINISH). ### Suspended session — `store/sessionStore.ts`


**⚠️ IT SURVIVES THE APP BEING KILLED (July 30 2026).** The store is plain in-memory zustand, so a force-quit — or iOS reclaiming the app mid-workout, the common one — took the header timer chip with it. The session was never lost (the `in_progress` row is on the server, the numbers are in the draft), but the fastest way back to it was, and a client who cannot see their session assumes it is gone. `suspendSession` / `clearSuspendedSession` now **write through to AsyncStorage**, and `hydrateSuspendedSession(userId)` — awaited in `app/_layout.tsx` before it routes — brings the chip back. **Keyed by the SIGNED-IN user via `bindSuspendedSessionToUser` (AuthContext, beside `bindCardVariantToUser`)**: a trainer's suspended session is stored under the CLIENT's id, so keying by `clientId` would hand it to the wrong account on a phone that runs both. **⚠️ Both hydration checks are deliberately LOCAL — this runs at launch, and the phone that just lost the app mid-workout is often the one with no signal:** (1) **started today**, because `load()` only ever adopts today's `in_progress` row, so an older chip would lead somewhere that refuses to resume and would show an hours-long clock getting there; (2) **the draft still exists** — every path that ends a session (finish, discard) clears it, so its absence IS the local record of "this session is over". Do not replace either with a `sessions` query. **Killed while INSIDE Do Mode is the other half and needs no chip:** `suspendSession` was never called, but `lib/lastRoute` restores the route, so the app reopens in the session itself. **⚠️ Free sessions get no chip back** — the check hangs off the draft, and free sessions have none (see the free-session note below).

- `resume()` sets `startedAt` to the **original** timestamp (not `Date.now()`), so the elapsed timer continues from where it was.
- Do mode detects `resumeSessionId` + `resumeStartedAt` URL params on mount: sets `activeSessionId` to the existing DB row and calls `resumeSession()` with the original startedAt. Guards by `resumeAutoStarted` ref.

### Warm-up sets — "W" instead of a number (July 27 2026, BOTH sides + builder)
Vitek's ask: *"i would like to make clear for my clients that some sets are only warmup sets, the first ones — usually it would be first set but it could be also three sets."* A set can now be flagged a warm-up; it sits at the TOP of the exercise and its set-number column reads **`W1` · `W2` · `W3`** (ACCENT, `setNumWarmup` — numbered on Vitek's call: *"there can be w1 w2 w3?"*; three identical Ws say nothing about which one you're on), so the **working sets still read 1 · 2 · 3** — his call over W · 2 · 3 · 4.

- **⚠️ THE NUMBERING RULE (`lib/warmupSets.ts` is the ONLY definition — do not inline a second copy):** `set_number` is counted **within its own block**. Warm-ups are 1..n, working sets are 1..m, so one exercise legitimately holds a warm-up 1 AND a working set 1 — **the pair `(set_number, is_warmup)` identifies a set.** This is deliberate: it means flagging a new warm-up onto a workout the client has already done can never shift set 1's logged weight history onto set 2. The alternative (one sequential run, renumbering the display) was rejected for exactly that reason. It also means W · 1 · 2 · 3 falls out for free — nothing is renumbered at render time.
- **⚠️ CONSEQUENCE: every map keyed by set number must be keyed by `setKey(setNumber, isWarmup)`** — including **`logIdByKey` in the trainer's off-session save**, which was missed in the first cut and produced the sharpest symptom of the lot: warm-up 1 and working set 1 both hashed to `weId:1`, the map kept whichever log row came last, and a weight corrected on a working set was written onto the warm-up's log row (Vitek: *"the weight for the two working sets suddenly appear in the first two warm up sets … i think the app doesnt see the difference between warm up set and normal set"*) — (`isWarmup ? -setNumber : setNumber`), never the raw number — otherwise the warm-up's 20 kg pre-fills working set 1. Already done in: both Do Mode files' first-session peek / trend / cross-workout pre-fill maps (each is one `const setNum = setKey(...)` line feeding the whole block, plus the `${weId}:${n}` trend composite key), the builder's `fetchLastPerformedMap`, and `SetHistoryModal`'s `highlightSetNum` (which is a setKey now, not a set number). **Every read of workout_sets / template_sets / session_logs orders `is_warmup DESC, set_number ASC`** (`compareSets` for in-memory sorts).
- **DB:** `is_warmup BOOLEAN NOT NULL DEFAULT false` on **`workout_sets`, `template_sets` and `session_logs`** — migration `20260727000001_add_warmup_sets.sql`. All three matter: the workout holds the plan, the template carries it through a deep-copy, the log records what was actually done as a warm-up.
- **Marking one — three entry points, because Vitek changes his mind mid-session** (*"i will change it on the spot often, while running the workout or before"*):
  1. **Workout builder — tap the set NUMBER** to flip `1` ⇄ `W` (`toggleWarmup`). Vitek's reasoning splits by side and both land on the same control: *"for me that mirrors the way i work usually as a trainer and for the clients it doesnt mirror how they usually work so the extra start should be in place."*

It clears `pendingLogDate` first: `createInProgressSession` reads that for the row's `date` even on the free path.

### Free sessions — a workout is created BEHIND them (July 30 2026)

**They could not save their numbers AT ALL before this, and it was never the missing draft.** An exercise added mid-session is created with a **local** `workoutExerciseId: uid()` and only becomes a real row through `addedExercises` — which `saveSession` hardcoded to `[]` for free sessions (`const addedExercises = isFreeSession ? [] : …`, both files), and `lib/sessionOutbox` skipped that stage too (`&& !job.isFreeSession`). So every log was built with `weIsLocal: false` and a `workout_exercise_id` that had no row behind it, while **`session_logs.workout_exercise_id` is `NOT NULL REFERENCES workout_exercises(id)`** (`20260423000000_initial_schema.sql:138`). The insert failed on the FK → the July 29 hard-requirement path reverted the session to `in_progress` → **the job requeued forever.** Photos taken on those exercises were silently dropped by the same empty `addedLocalIds`. Never reported because the client cannot add exercises to a free session at all (the floating `+` is `isFreeSession && isTrainer`) and the only free session in the live DB was a 7-second test from 16 May 2026 with zero logs.

**Vitek's call: "the free session should create a workout behind it."** So:
- **`FinishJob.freeWorkoutId`** — minted **on the device** in `saveSession` (only when the free session actually has exercises), for the same reason the session id is: a request can time out *after* the server applied it, and an insert would leave the client two identical workouts. The outbox **upserts** it: `name` = the free-session name, `status: 'completed'` so it stays out of the active list, `created_by = authorId ?? clientId`.
- **Stage order matters** — the workout is created BEFORE the session stage, because that stage now points `sessions.workout_id` at it. ⚠️ That link is what makes the workout's "last done", its history and its progress read correctly; an unlinked workout would sit in the list claiming it had never been performed.
- `addedExercises` no longer excludes free sessions; the outbox resolves `targetWorkoutId = isFreeSession ? freeWorkoutId : workoutId` and everything downstream (sets, logs, photos, `realWeId`) works unchanged.
- **⚠️ RLS: the client got that `+` on July 30 2026, so the policy the old note here warned about now exists** — `20260730000001_client_adds_exercises.sql`. `workouts` and `workout_exercises` were trainer-insert-only ("workouts: trainer all"; clients only SELECT their own); the client now has INSERT on `workout_exercises` for a workout that is theirs, and INSERT **+ UPDATE** on `workouts` where `client_id = created_by = auth.uid()`. **UPDATE is not a separate capability — the free-workout stage `upsert`s**, and `INSERT … ON CONFLICT DO UPDATE` needs an UPDATE policy for the conflict path, which a retry after a timeout will hit. Scoping UPDATE on `created_by` as well as `client_id` is what keeps a trainer-authored workout read-only to the client it is assigned to. **Every stage is a hard requirement, so a missing policy does not lose the session quietly — it requeues the job forever.**
- **⚠️ Client REPLACE and DRAG-REORDER needed a second migration — `20260730000002_client_replace_and_reorder.sql` (device-confirmed broken, then applied).** Both have been in the client UI for months and both write `workout_exercises`, which was trainer-only for UPDATE. **Under RLS that is not an error — it matches ZERO ROWS**: the request succeeds, reports nothing, changes nothing, and the outbox does not check those particular errors either, so nothing requeued and nothing surfaced. Vitek found it by swapping an exercise as a client, finishing, and reopening the workout to the original. **⚠️ Unblocking `workout_exercises` alone would have been the WORSE bug:** a replacement is recorded across FOUR tables — `workout_exercises` + `workout_exercise_slots` (upsert, so INSERT **and** UPDATE) + `slot_replacement_history` + `slot_order_history` — and three of them were blocked too, so the swap would have stuck while its history silently vanished, leaving the Info panel unable to say what was replaced and when (the §6 slot tracking is the point of those rows). The migration covers all four, gated on the workout belonging to the client, and grants **no DELETE anywhere** — deleting an exercise stays trainer-only, and the app-wide rule is that a removal is a soft `is_active` delete regardless.
- **⚠️ THE LESSON, which cost a device round: a Supabase write blocked by RLS is SILENT.** It is not an exception and it is not an error object — the row simply is not visible to the statement, so an UPDATE reports success having touched nothing. Any client-side write added to a table whose policies are trainer-shaped will behave exactly like this. When a client action "works during the session and is gone next time", check the policies before the code.
- **Drafts + resume now cover free sessions too:** the draft effect no longer excludes them (`workoutId` is the literal `'free'`, so the key is `…:free` — the one the finish/discard paths already cleared), and `load()`'s free branch **adopts an open `workout_id IS NULL` `in_progress` row** with the same rules as the workout path (today's row by `date`, never `created_at`; never one someone else started) and replays the draft over it. ⚠️ The free auto-start effect now returns early when a session was adopted or `resumeSessionId` is present — **and must NOT call `startSession()` there**, which is the store's `start` and would stamp `startedAt = now`, throwing away the original clock. The client-side free insert was also missing `started_by`, so nothing could tell whose session it was.
- Not changed: `session-complete` still receives `workoutId: 'free'`, and every use of it there is already guarded by `isFreeSession` / `!== 'free'`. A free session therefore gets records compared per exercise across all workouts (the normal rule) but no "WORKOUT BEST" scope — correct, since it is not a repeatable workout.

- **`lib/sessionDraft.ts` (NEW)** — `saveSessionDraft` / `loadSessionDraft` / `clearSessionDraft` / `mergeDraftIntoExercises`, backed by AsyncStorage, key `sessionDraft:v1:{clientId}:{workoutId}`, drafts older than 36h are purged on read. The draft holds the **whole `exercises` array** plus `barbellWeights` / `machineBrands`, `activeSessionId` and `startedAt`. Written by a debounced (500ms) effect on every `exercises` change while a session is running.
- **`mergeDraftIntoExercises(loaded, draftExercises)`** — the DB row stays the source of truth for anything the session can't change (names, media, notes, targets, first-session peek data); the draft supplies only what the session produced: entered weight/reps, done marks, removed/added sets, and exercises **added mid-session** (no DB row at all → carried over from the draft wholesale). Sets match on `workoutSetId`; exercises on `workoutExerciseId`; draft order wins, loaded-but-not-in-draft exercises are appended.
- **`load()` adopts an open `in_progress` session.** It queries the newest `in_progress` `sessions` row for this client+workout and, unless view-only / a `resumeSessionId` param is present / the client is deliberately logging a past day (`pendingLogDate`), sets `activeSessionId` + `resumeSession(...)` from the draft's `startedAt`. **Guarded to TODAY's row** — a forgotten in_progress row from a previous day must not resume with a multi-day timer. This also kills the duplicate-session class of bug: back-swiping out and re-entering no longer leaves an orphan row and inserts a second one.
- **⚠️⚠️ THE "TODAY" TEST READS `sessions.date`, NEVER `created_at` (fixed July 28 2026 — this was a live data-loss bug).** A **planned** session is not inserted when it is performed: `createInProgressSession` **converts the trainer's `scheduled` row** (status → `in_progress`, `date` → today) and **leaves `created_at` at the moment the trainer made the plan, days earlier**. The old test — `new Date(created_at).toDateString() === today` — therefore returned **false for every planned session**, so the running row was never adopted: `activeSessionIdRef` stayed null, the draft was never replayed (it is gated on `liveSessionId || resumeSessionId`), and **the client's weights and reps were wiped on any mid-session reload** while notes and photos survived — i.e. exactly the symptom the draft was built to fix, silently reintroduced for the one case a client actually hits. Pressing START again then INSERTED a second row, because the scheduled lookup no longer matched. It never showed up in testing because an ad-hoc start creates its row today, so `created_at` and `date` agree; **only a trainer-planned session performed on a later day breaks the equivalence.** Both Do Mode files now select `id, created_at, date` and compare `date` to `YYYY-MM-DD`. `created_at` survives only as the resumed-clock fallback when the draft has no `startedAt`, and **only if it is itself today** — otherwise the timer would open showing days elapsed; it falls back to `Date.now()`. **Rule: on a `sessions` row, `date` is the training day and `created_at` is a bookkeeping timestamp. Never use `created_at` to ask "is this today's session?"**
- **⚠️ "Discard session" must NOT delete a converted plan (fixed July 28 2026, both files).** It ran a hard `sessions.delete()`, so a client abandoning an attempt **destroyed the trainer's planned session for that day** — it is the same row. `sessionFromPlanRef` + `sessionPlanDateRef` are set in the conversion branch (and mirrored into the draft as `fromPlan` / `planDate`, so the origin survives the app being reclaimed); discard then deletes the session's `session_logs` and puts the row **back to `status:'scheduled'` on its original date** instead of deleting it. A session that really was inserted for this attempt is still deleted. Vitek's rule: *"discard session just deletes what was added but doesnt delete the planned session, that is a different button — delete workout in the three dots menu."*
- **The draft is only replayed when a session is actually open** (`liveSessionId || resumeSessionId`) and its `activeSessionId` matches — never over a fresh start. Cleared on successful FINISH and on "Discard session".
- **⚠️⚠️ FINISHING IS A LOCAL ACT; UPLOADING IS A BACKGROUND CHORE (July 29 2026, both files + `lib/sessionOutbox.ts`).** Finish used to mean *"write it to the server, and only then is the session over"* — so with no connection the session could not end at all. A client mid-session: *"no message appeared, it just went away and then he tried it again, and the window went away and the countdown continued"*, then he left the session running and force-quit the app. Vitek's framing is what settled the design: **people train in the same spot every week, so someone who finishes without signal almost certainly STARTED without signal** — "wait for the connection to come back" is a bad bet, and an in-screen retry was treating the symptom.
  - **`lib/sessionOutbox.ts` owns the whole finish.** `saveSession` builds one serialisable **job** (session row + logs + added exercises + extra sets + replacements + slot history + notes + photos), `enqueueFinishJob` writes it to AsyncStorage — a write that cannot fail for network reasons — and *that* is the save. The session ends immediately: `finishSession()`, draft cleared, **no IN PROGRESS card left behind**. `flushSessionOutbox()` uploads it: once inline (bounded by `IMMEDIATE_UPLOAD_WAIT_MS`, 12 s, so a working connection lands inside it), then from **`app/_layout.tsx`** on sign-in and on every return to the foreground. It lives at the root deliberately — the previous in-screen retry timer died with the screen.
  - **⚠️ THE SESSION ID IS MINTED ON THE DEVICE** (`generateUUID()`, or the running row's id). That single decision is what makes the rest work: the session has an identity before the server knows it exists, so every write is addressed by id, each stage is idempotent, and a half-uploaded job **resumes** instead of duplicating. Never go back to "insert, then learn the id".
  - **⚠️ EVERY STAGE MARKS ITSELF DONE ONLY WHEN IT ACTUALLY SUCCEEDED.** The first cut treated the tail (extra sets, notes, photos) as best-effort — marked done regardless of error, "because the session itself was safe". A replay test that cut the connection after N writes showed what that meant: **a set added mid-session and a photo the client took were dropped permanently**, first failure, no retry. Anything short of every stage landing leaves the job queued. `session_logs` is delete-then-insert so a replay can never double a set (a request can time out *after* the server applied it), and added exercises record their real id (`realWeId`) and their sets (`setsDone`) separately — folding the sets into the exercise's own step made a resumed job skip straight past them.
  - **⚠️ THE OUTBOX DEPENDS ON THE REQUEST DEADLINE IN `lib/supabase.ts`.** `flushSessionOutbox` guards itself with a module-level `flushing` flag cleared in a `finally` — so an upload that never settles latches it true forever, and every later flush (app start, foreground, the next finish) returns immediately having done nothing. Without the deadline the outbox is disabled by exactly the connection it exists to survive. The deadline is also what the rest of the app relies on: the outbox only covers FINISHING, and every other screen still fetches live (the Training tab hanging after that same client left his session is the other half of the incident).
  - **`isSessionPending(sessionId)` is narrower than "is it queued"** — it asks whether the session row and its logs are still stuck on the phone. A job hanging around for one unsent photo must not make Finish claim there is no internet.
  - **What the client sees.** Uploaded in time → the Session Complete overview, exactly as before. Not uploaded → a glass confirm, *"Session saved on your phone — no internet right now; every weight and rep is logged and will upload by itself as soon as you are back online. The session overview will be there then."* → Done → back. The overview needs the client's whole history to work out records, which is why it waits rather than rendering an empty one.
  - **Deleted by this, do not reintroduce:** the in-screen retry `setInterval`, the "Waiting for connection…" footer state, the resume-a-owed-finish-on-load path and its `finishRequestedAt` draft field, and the "Couldn't save the session" failure modal (that title now only appears if the *device storage* write fails, which is not a network problem). `finishRequestedAtRef` survives as the session's END TIME — stamped when Finish is confirmed (`requestFinish`), reused by nothing else, `Math.max(0, …)`-clamped — so a session that sits in the outbox for five hours is still recorded as the hour that was trained.
  - **⚠️ `savingSession` + `savingSessionRef` — Finish must show that it is working, and must not be re-entrant.** Finish had no state of its own (unlike "Save changes" right beside it), so a slow save was indistinguishable from a dead button — which is why the client tapped it over and over. It now shows **"Saving…"** with a spinner and is disabled while it runs. The **ref** blocks re-entrancy, which previously let two overlapping saves each finalise the row and each insert a full set of `session_logs` (every set logged twice).
  - **⚠️ The `session_logs` insert is a HARD REQUIREMENT.** It used to only `console.log` its error, so a finalised row with zero logs read as "saved" everywhere while the weights were gone. On failure the row goes **back to `in_progress`** and the whole save fails. Still unaddressed by design: if a later step throws after step 1, `completedSessionId` is already set, so the `finally` takes the SUCCESS branch — session marked `completed` with zero logs, reported to the user as saved.

### ⚠️ A logged weight REQUIRES reps (July 28 2026, both Do Mode files)
Vitek: *"kg and no reps should not exist, so if i record weight and no reps and click like done the app should say you need to record a rep. reps without weight are ok."* Ticking a SET done, or the exercise's done circle, is **blocked** when any non-removed set has a weight but an empty reps box; a toast says so (`repsToast`, reusing `pendingDoneToast`'s styles) and the tick does not happen. Reps with no weight stay valid — that is bodyweight work. **Why it matters beyond tidiness:** the session summary's records compare weight AND reps, and a weight-only row can't be judged (it also printed as `0 × 40 kg`, reading as zero reps). Historic rows still have this shape, hence `setLabel()` in `SessionCompleteScreen`.

### Rest timer — slide-up panel + running pill (July 2026)

The rest timer was a centered `Modal` whose dismissal (tap-outside / back) **cleared the interval**. It is now a slide-up panel that keeps counting when hidden.

- **`RestTimerSheet`** (module-level in both Do Mode files) — `useSheetDismissGesture` + `KeyboardAvoidingView flex-end`, drag handle, `restSheet` white sheet. **All countdown state stays in the screen** (`restRunning / restRemaining / restTotalSecs / restOvertimeSecs / restInputText / restApplyAll` + the `restRef` interval) and is passed in as props — that is what lets the clock outlive the panel. Rendered conditionally (`{restVisible && <RestTimerSheet …/>}`) so the slide-in re-fires each open. Two drag-target fixes: `restSheet` centres its children, which would shrink the handle's hit area to the 36px pill — the handle wrapper is `alignSelf:'stretch'` so the whole top strip drags; and **while counting** the ring itself carries `sheetPan` (nothing in it is interactive then, and it's the obvious thing to grab).
- **Dismiss ≠ cancel.** Swipe-down / tap-outside / the "Hide — keeps counting" link only unmount the panel. Only **Stop** (in the panel) or the **✕ on the pill** call `stopRest()`, which clears the interval.

### "Save changes" — off-session save, TRAINER FILE ONLY (`0c8b5f9`, July 27 2026, Vitek — DEVICE-CONFIRMED, "it works the save button")

**The problem:** between sessions there was no way to record a weight the trainer forgot to log or a note he forgot to write. The only route was start-a-session-and-finish-it, which *invented an extra session* (wrecking the session count with the client) and re-dated every note, so nothing showed up as a reminder in the next training. Same gap after just building a workout: edits couldn't be saved without performing it.

**The fix:** while **no session is running**, the list-footer slot that later holds "Finish session" holds a **"Save changes"** pill instead (`styles.finishFooterBtn` reused; `saveFooterBtnIdle/TitleIdle/SubIdle` grey it out when nothing is pending — it stays visible so the button is discoverable where the trainer expects it). Sub-line names the destination: `To the session of 24 Jul` / `To this workout` / `Nothing to save yet`. Rendered on the non-edit `FlatList` only, gated `!isRunning && !pastSession && !isFreeSession && !loading`. **Client file has none** — the client logs by performing.

- **Where the numbers go.** `lastCompletedSession` (id + date, set in `load()` from `recentSessData[0]`) is the target. With a completed session → `session_logs` for THAT session id: existing `(workout_exercise_id, set_number)` rows are UPDATEd, a set that session never logged is INSERTed. **No session ever performed** → the numbers become the workout's own starting numbers (`workout_sets.target_weight_kg` / `target_reps`), which is what a builder save writes — "as if registered at the creation of the workout". Local `targetWeightKg`/`targetReps` are updated too so the input placeholders match.
- **⚠️ Dirty tracking is PER FIELD, not per set** (`offSessionDirtyFields`, `${weId}::${setLocalId}::${weightKg|repsCompleted}`, marked in `updateSet` via `markOffSessionDirty`). The inputs are pre-filled from the client's most recent logs **across workouts** — writing an untouched field back would stamp another workout's number onto this session's history. Only edited fields go into the patch. For the same reason an UPDATE never re-writes `barbell_weight_used_kg` / `machine_brand` (that session's own record); an INSERT does supply them.
- **Number corrections apply to** sets that already exist in the program (`workoutSetId != null`, non-dropset) on non-added exercises.
- **Program changes Save also commits** (`addedExercises` / `replacedExercises` / `addedSets` on `offSessionChanges`): an exercise added via swipe → Add below (insert `workout_exercises` + its `workout_sets`), an exercise swapped via swipe → Replace (update `exercise_id` + `workout_exercise_slots` upsert + `slot_replacement_history`), and sets added with the card's `+`. Each row is inserted **one at a time with `.select('id').single()`** — a bulk insert can't be matched back to a local set, because dropsets repeat their parent's `set_number`. The returned ids are written back into state (`realExerciseIds` / `realSetIds`) so a second Save doesn't insert everything twice; **deliberately not a `load()`**, which would re-fire the order-mismatch and last-session-notes popups and re-read numbers still being typed. Typed numbers on those brand-new sets go into the target session too (`freshLogs`), or become the set's `target_*` when no session exists yet. New rows get `is_added_during_session: false` — this is a program edit, not a mid-session one, so no false "Added ·" label appears.
- **These already persist the instant you do them and need no Save:** deleting an exercise, drag-reorder (`persistDragReorderAsync`), and making/breaking supersets.
- **⚠️ REMOVING A SET IS A PROGRAM CHANGE OFF-SESSION (changed July 27 2026).** It used to stay a session-level "skipped this time" — the `workout_sets` row survived and the set was back next time. Vitek caught it on device: *"i deleted sets and saved it … but then when i came back the sets were still there, the new warm up sets were saved. only the deleting of the sets didnt work."* Two reasons it was wrong: off-session there **is no session** for a set to be skipped in, and the same Save button persists ADDED sets — so `+` stuck and `−` silently didn't. Now `removedSets` (real `workoutSetId`, non-dropset, on a non-added exercise) **`DELETE`s the `workout_sets` rows**. A hard delete is safe here and matches the builder (which replaces `workout_sets` wholesale): `session_logs` hang off `workout_exercise_id`, **not** off a set row, so no logged history cascades — unlike the exercise delete below. A set being removed by this Save is **excluded from the dirty-value collector**, so it can't also write its numbers into the session on its way out.
- **⚠️⚠️ THE SURVIVORS ARE NOT RENUMBERED — and that is the whole point.** The first cut renumbered them 1..n per block so the card wouldn't read `1 · 3`. Vitek found it immediately: deleting sets 1–3 of 5, *"the weights were from the first two that were deleted not from the last that stayed."* Cause: **`session_logs` records a set by its NUMBER, not by its `workout_sets` id** — so a set's weight memory is tied to its POSITION. Pulling set 4 down to 2 hands it set 2's logged history. Migrating the logs instead is not an option either: the deleted sets' logs still occupy those numbers, and moving them aside would either collide or destroy what the client actually lifted. So **the stored numbers keep their gaps (1, 2, 4, 5) forever**, every set keeps its own history, and **`buildSetLabels` (lib/warmupSets.ts) closes the gap on screen** — the card counts positions and still reads `W1 · W2 · 1 · 2 · 3`. Three consequences to hold onto: (1) **`setNumber` is an IDENTITY, the label is a POSITION** — all four set-row surfaces take a `displayLabel` prop and no longer print `set.setNumber`; (2) a new set takes **`nextSetNumber()` = max + 1 within its block**, never `count + 1`, which would collide with a gap; (3) the **set-HISTORY views deliberately still print the stored number** via `setLabel()` — they show a past session, and that is what the set was called in it. Local state drops the removed sets and applies the new numbers rather than reloading. **Inside a RUNNING session removal still means "skipped this time"** (`saveSession` logs `is_removed: true`, row survives) — that distinction is deliberate, skipping a set today is not the same as changing the program.
- **⚠️ Deleting an exercise in Do Mode is a SOFT delete since July 27 2026** — `deleteExerciseFromWorkout` / `deleteSupersetGroup` set `is_active = false` instead of `DELETE`. The hard delete they used to do cascaded the row's `session_logs` and erased what the client had actually lifted on that exercise, breaking the app-wide soft-delete rule the builder follows. Exercises added in this visit have no DB row yet (their id is a local `uid()`, not a UUID) — those are just dropped from state, no DB call.
- **Notes.** Exercise- and set-level notes already hit the DB the moment they're typed (they hang off `workout_exercise_id` / `workout_set_id`, not off a session), so Save has nothing to write for them — but `markOffSessionNoteTouched()` is called from every note add/edit/delete handler so the button still **lights up**, otherwise writing a note and reading "Nothing to save yet" looks like the note was lost. Save does commit the pending work: soft-deleted persisted notes (+ the exercise-detail bridge queue via `flushPendingNoteDeletes`) are really deleted, and **training notes**, which need a session to point at, are inserted with `reference_id = lastCompletedSession.id` — which is exactly what the next session's "Notes from last session" popup reads. With no completed session there is nowhere to put a training note, so it stays unsaved (weights still save).
- **Confirm before writing** (glass `confirmModal`) **itemises what goes where**, because the program half and the history half land in different places and one of them rewrites the past: `• 1 exercise added to the workout` / `• 1 set removed from the workout` / `• 2 sets corrected in the session of 24 Jul`, then "No new session is started and the session count stays the same." A failure keeps everything typed and offers **Try again**, same as `saveSession`. Success → a toast (`savedToast`, own `savedToastTimerRef` — sharing `toastTimerRef` with the "not marked as done" toast left whichever one it belonged to stuck on screen) and the screen **stays put**; nothing navigates.
- `offSessionDirtyFields` is cleared whenever `startedAt` becomes set — once a session is running the edits belong to it and FINISH writes them.

### Done-circle behaviour
Tapping the circle marks the exercise done **and every one of its sets**, then **auto-navigates to the next unchecked exercise** — forward from the current index, wrapping to the start. If all are done → custom confirm "All exercises done! Finish the session?" (Cancel / Finish); Finish calls `setPendingFinish(true)` then `router.back()`, and **Do Mode reads `getPendingFinish()` on focus** and runs its own `handleFinish`. Tapping an already-checked circle unchecks the **exercise only** — its sets stay as they are.

### Bridge — syncing state back to Do Mode (`lib/doModeBridge.ts`)
- Set field changes → `addPendingSetUpdate()` · barbell weight → `addPendingBarbellUpdate()` · checkmarks → `addPendingCheckUpdate()`. All are flushed in Do Mode's `useFocusEffect` via `flushPendingUpdates()` and applied to `exercises`.
- Direct callbacks `notifySetsChanged` / `notifyCheckChanged` are **also** registered from Do Mode, so edits appear immediately instead of waiting for the focus effect.
- **⚠️ THE BRIDGE RULE: every bridge callback must be called OUTSIDE any `setState` updater.** Pre-compute the next array from `setsRef.current`, then call `setSets(next)` and `notifySetsChanged(...)` as separate statements. Calling one inside an updater throws "Cannot update a component while rendering". Same for `notifyPhotosChanged`.
- **`sessionId`** is passed as a URL param from Do Mode as `activeSessionIdRef.current ?? ''` — required for photo upload, empty string when no session is running.

### Other rules
- Hard block modal: custom centered glass popup (state: `hardBlockModal`) — NOT `Alert.alert`.
